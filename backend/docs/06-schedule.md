# 계획 일정 결정 사항

> 계획 일정(API-036~040·084)을 만들면서 정한 규칙이다. 원천은 팀 Notion "API 명세"이고, 명세에 없는 값은 여기 적는다.
> 명세와 이 문서가 다르면 명세를 먼저 고치고 이 문서를 맞춘다.

## 1. 흐름

| 단계 | API | 비고 |
| --- | --- | --- |
| 조건 입력 → 초안 생성 | 037 | 비동기(202). 날짜가 정해지고 후보가 3곳 이상일 때 |
| 초안 조회 | 038 | |
| 서버 재계산 미리보기 | 084 | 선택. 사용자가 "다시 계산"을 누를 때만 |
| 편집한 초안 저장 | 039 | 전체 편집 상태를 한 번에 보낸다 |
| 확정 일정 조회 | 036 | 022 의 `schedule` 도 같은 구조 |
| 확정 일정 직접 편집 | 040 | 화면의 "일정 조정하기"는 040 이 아니라 037(`fixedItems`) → 084 → 039 를 쓴다 |

## 2. 결정 사항

### 조건 (11/6)

- **하루 일정 밀도(pace)는 없앤다.** 여유롭게·보통·빼곡하게 선택을 받지 않는다.
- **출발·도착 지점**은 첫날 출발지(`startPoint`)와 마지막 날 도착지(`endPoint`) 둘만 받는다. 둘 다 선택이다.
  - 역·터미널을 받을 것으로 보지만 종류 제약은 두지 않는다(혼자 여행이면 집일 수도 있다).
  - 숙소는 따로 받지 않는다. 그 밖의 날(중간 날, 첫날 도착, 마지막 날 출발)은 지점이 없다.
  - 당일치기는 같은 날에 출발지와 도착지를 모두 적용한다.
  - 지점이 없는 날은 첫 장소에 그날 시작 시각으로 도착하고, 마지막 장소 뒤에는 이동 구간이 없다. 임의 지점을 만들지 않는다.
- **체류 시간**은 새로 배치할 때 60분이고, 사용자가 **1분 단위로 1~720분**(최대 12시간) 사이에서 고칠 수 있다.
  0분·720분 초과는 C003, 음수는 SC006. DB 에도 `CHECK (stay_minutes BETWEEN 1 AND 720)` 이 있다(ERD).
- **도착·출발 시각은 사용자가 정하지 않는다(11/6).** 항상 "그날 시작 시각(또는 직전 출발) + 이동 시간"으로 계산하고,
  출발 = 도착 + 체류 시간이다. 사용자는 앞 장소의 체류 시간을 늘려 뒤 시각을 조정한다. 그래서 040 요청은 `arrivalAt` 을
  받지 않고(보내도 무시), 재계산하면 시각이 새로 매겨진다.
  - 일차 시작 시각이 없는 날은 기준 시각이 없어 도착·출발 시각이 `null` 이고 `ARRIVAL_TIME_UNKNOWN` 경고가 붙는다.
    근거 없는 시각을 만들지 않는다는 명세 정책에 따라 기본 시작 시각(예: 09:00)을 두지 않는다.

### 식사 배치 (11/6, 초안 생성 037 에 적용)

- 맛집은 후보의 카테고리가 `FOOD` 인 장소다. 카테고리가 없는 후보(지도 핀 직접 추가)는 맛집으로 보지 않는다.
- 점심은 **도착 시각이 11:00~14:00** 사이가 되도록 넣는다.
- 저녁은 **도착 시각이 17:00~20:00** 사이이면서 **그날 점심 도착 시각 + 5시간 이후**가 되도록 넣는다. 그날 점심이 없으면 시간대 조건만 본다.
  - 5시간은 "밥이 들어갈 만큼 띄운다"는 뜻의 대략값이다. 기준은 도착 시각으로 정했다.
- 맛집이 모자라면 **모든 날의 점심을 먼저** 채우고, 남는 맛집으로 저녁을 채운다.
- 그날 시작~종료 시각 안에 식사 시간대가 들어가지 않으면 그 끼니는 넣지 않는다.
- 식사 여부는 응답에 따로 표시하지 않는다(점심 태그 없음). 항목은 다른 장소와 같은 모양이다.
- 식사 시간대에 맞추려고 기다리는 시간을 넣지 않는다. 순서를 바꿔 맞추고, 못 맞추면 그대로 둔다.
- 084·039 는 사용자가 정한 배치를 그대로 계산한다(식사 배치를 다시 하지 않는다).

### 초안 생성 (API-037)

- 요청 확인은 바로 하고(오류는 그 자리에서 4xx), 배치·시각 계산은 비동기 작업으로 한다. 202 로 `jobId`·`draftKey` 를 준다.
- `roomPlaceIds` 는 **현재 담은 후보 전부**(뺀 후보 제외)와 같아야 한다. 빠지거나 겹치거나 다른 후보면 C003. 3곳 미만 C003.
- `days` 는 여행의 모든 날짜를 중복 없이, 날마다 시작 < 종료(아니면 C012). 날짜 미정·이동 수단 없음은 C003.
- 항목: `fixedItems` 를 요청 순서대로 먼저 만들고(itemId 1부터), 나머지 후보를 `roomPlaceIds` 순서로 하나씩 만든다.
  `fixedItems` 에 있는 후보는 따로 더 만들지 않는다.
  - `fixed=true` 는 그 날짜·순서 자리에 둔다. `fixed=false` 는 그 날짜에 두되 순서는 다시 정한다.
- 체류 시간: `fixedItems` 는 그 값, 나머지는 `stayMinutes` 맵 값, 없으면 60분.
- `mealConstraints` 는 명세가 "상세 미정"이라 읽지 않는다. 식사 배치는 위 규칙을 항상 쓴다.
- 배치 순서
  1. **날짜 나누기**: 직선 거리로 가까운 후보끼리 날짜 수만큼 묶는다. 하루에 쓸 수 있는 시간(체류 + 장소마다 예상 이동 20분)을
     넘기지 않고, 날짜마다 그날 시간에 비례한 장소 수(올림)까지만 먼저 채운다. 가까운 후보가 한쪽에 몰려도 한 날에 다 넣지 않는다.
  2. **맛집 나누기**: 날마다 필요한 끼니(점심 → 저녁 순)만큼 맛집이 남는 날에서 가까운 맛집을 옮긴다.
  3. **날짜 안 순서**: 그날 장소끼리만 길찾기로 이동 시간을 구하고(캐시), "이동 합계 + 식사 못 맞춤 벌점 + 종료 시각 넘김 벌점"이
     가장 작은 순서를 고른다. **10곳 이하는 모든 순서를 비교**하고(명세), 그보다 많으면 가까운 곳부터 잇고 2-opt 로 다듬는다.
  4. **시간 넘김**: 종료 시각을 넘기면 고정하지 않은 항목을 하나씩 미배치로 뺀다(맛집은 마지막에). 고정 항목만으로도 넘치고 그날
     이동 시간을 모두 알면 작업이 SC002 로 실패한다.
- 이동 시간을 모르는 구간은 **순서를 고를 때만** 직선 거리로 어림한다(우회 1.3배, 자동차 40km/h·대중교통 20km/h). 결과 시각에는
  쓰지 않는다(그 구간은 `null` + 경고).
- 하루 10곳 비교는 테스트 기준 1초 이내다(근사 해로 처음 상한을 잡고 이동 시간 행렬로 가지를 친다). 장소 쌍마다 길찾기를 부르므로 하루 k곳이면 최대 k(k−1)+2k 번이다(캐시 제외).

### 초안 조정·저장 (API-084·039)

- **084**: 바꿀 항목만 보낸다. 같은 날짜 순서는 1부터 다시 매기고, 보낸 항목이 그대로 둔 항목과 순서가 겹치면 SC005(040 과 같은 규칙).
  맨 앞에 넣으려면 그날 다른 항목의 순서도 함께 보낸다. 모든 일차를 다시 계산하고(같은 구간은 캐시), 종료 시각을 넘기는 날은
  고정하지 않은 마지막 항목부터 미배치로 옮긴다. 지점은 생략하면 그대로, `null` 이면 해제한다.
- **039**: 초안 항목 전체가 `days[].items` 나 `unassignedItemIds` 중 정확히 한 곳에 있어야 한다(아니면 C003). 순서는 1부터 빈 번호
  없이(겹치면 SC005, 비면 C003). 알려진 시간으로 종료 시각을 넘기면 SC002 이고 항목을 옮겨 성공시키지 않는다.
  기존 확정 항목은 모두 지우고 요청한 배치로 새로 넣는다.
- 같은 초안의 084 처리 중·039 처리 중에는 다른 084·039 가 SC003 이다(Redis `schedule-draft-lock:{draftKey}`, 수명은 작업 제한 시간).
- **재전송 보호**: 039 성공 시 `schedule_options.lastApplied` 에 draftKey·draftVersion·baseVersion·요청 해시·멱등키 해시·저장 뒤
  version 을 둔다. 같은 초안·같은 내용이 다시 오면 방 version 이 그대로일 때 저장 결과를 돌려주고, 내용이 다르거나 그 뒤 일정이
  바뀌었으면 C004. 040·023 이 일정 옵션을 다시 쓰면 `lastApplied` 는 사라진다(그때는 version 도 바뀌어 결과가 같다).

### 비동기 작업 (API-011)

- Redis `job:{jobId}` 에 상태·결과·오류를 둔다. 작업 종류마다 조회 권한 규칙을 둘 수 있고, 없으면 요청자 본인만 본다(J002).
- 일정 초안 작업(`SCHEDULE_DRAFT`)은 요청자 본인이면서 지금도 그 방 참여자여야 한다(아니면 J003).
- 규칙 위반으로 실패하면 그 오류 코드(예: SC002)로, 예상하지 못한 오류는 C014 로 남긴다. C014 만 `retryable=true`.
- 서버가 처리 도중 재시작돼 제한 시간을 넘긴 작업은 조회할 때 실패(C014, 다시 시도 가능)로 보인다. 초안도 처음 만들기면 실패,
  다시 계산이면 마지막 성공으로 보인다.
- 제안값: 작업 기록·초안 보관 24시간, 제한 시간 2분, 실행 스레드 2개(대기열 100). `application.yaml` 의 `yeogirok.job`·
  `yeogirok.schedule`.

### 명세와 다르게 읽은 것 (팀 공유 필요)

- **RO003**: 039·084 오류 표에 "계획 편집 권한 없음"으로 있지만, 참여자 권한이 모두 같아 RO002 로 알린다(오류 코드 주석과 같다).
- **038 최상위 `id`**: 예시에는 있지만 본문이 "초안은 roomId·draftKey 로 식별하고 별도 id 를 두지 않는다"라 넣지 않는다.
- **038 `error`**: 명세 미정. 011 과 같은 `{code, message}` 로 둔다.
- **038 `travelDataSource`**: 이동 시간을 받은 첫 구간의 출처(예: `KAKAO_CAR`). 받은 구간이 없으면 `null`.

### 응답 모양 (Notion 11/6 수정 반영)

- `Schedule` 에는 별도 `id` 가 없다. 방마다 일정은 하나이고 경로의 `roomId` 로 식별한다.
- 확정 `schedule_items` 가 한 개도 없으면 `schedule` 은 `null` 이다.
- `startPoint`·`endPoint` 는 `Schedule` 에 하나씩 있다(일차마다 두지 않는다). 지점은 `{name: string|null, latitude, longitude}`.
- `unassignedPlaces` 는 `roomPlaceId` 만 준다(초안은 `itemId` 도). 못 넣은 이유·추천 날짜는 주지 않는다.
- `warnings` 는 `ScheduleWarning` 코드 배열이다(API-036 "일정 응답 공통 규칙"). 같은 범위에서 같은 코드를 중복하지 않는다.

| 값 | 뜻 |
| --- | --- |
| `TRAVEL_TIME_UNAVAILABLE` | 그날 구간 중 이동 시간을 모르는 것이 있다 |
| `ARRIVAL_TIME_UNKNOWN` | 도착 시각을 모르는 항목이 있다 |
| `END_TIME_EXCEEDED` | 마지막 일정(도착지가 있으면 도착지 도착)이 그날 종료 시각을 넘는다 |

### 여행방 수정(API-023)과 일정

- 날짜를 줄이면 새 날짜 밖 항목을 확정 일정에서 지운다. 후보 장소는 그대로다.
- 저장할 때 **날짜나 이동 수단이 바뀌면** 남은 항목의 이동 시간·시각을 다시 계산한다. 날짜가 바뀌면 첫날 출발지·마지막 날
  도착지가 붙는 날도 바뀌기 때문이다.
- **재계산 필요(`scheduleNeedsRecalculation`, 11/10)**: 확정 일정이 있는 방에서 후보 목록이 바뀌면(담기 029·030·031, 빼기 032,
  복원 094) `true`. 일정이 없는 방은 그대로 둔다. 일정을 새로 저장하면(039, 040 직접 편집) `false`. 023 은 바꾸지 않는다.
  후보를 바꾸는 API 는 version 증가와 같은 UPDATE 로 켜서 version 이 한 번만 오른다.
- 일정이 있는 방의 시작일·종료일을 모두 지우면(null) 409 RO010. 미리보기(`previewOnly`)도 같고 방·일정·version 은 그대로다.

### 이동 시간

- 카카오 REST API 키 하나로 부른다(`KAKAO_REST_API_KEY`).
  - `CAR`: 카카오모빌리티 자동차 길찾기(추천 경로 요약)
  - `TRANSIT`: 카카오맵 대중교통 경로 조회 중 가장 빠른 경로. 경로가 없고 직선 2km 안이면 도보 경로로 대신한다
- 초는 분으로 올림한다. 출발 시각을 넣을 수 없어 시간대별 교통 상황·배차는 반영하지 않는다.
- 키가 없거나 호출이 실패하면 이동 시간을 `null` 로 두고 경고를 붙인다. 근거 없는 이동 시간·시각을 만들지 않는다(명세 정책).
- 2026-11-06 실제 키로 세 API 응답 모양을 확인했다.
- **캐시**: 같은 구간(출발·도착 좌표, 이동 수단)의 이동 시간은 서버 메모리에 6시간 기억한다(최대 1만 구간). 이동 시간을 구한
  결과만 기억하고, 서버를 다시 띄우면 비워진다. 대중교통 응답이 경로 좌표까지 담아 커서 재조회를 줄이려는 것이다.
- **호출 쉬기**: 자동차(카카오모빌리티)와 대중교통·도보(카카오맵)를 따로 본다.
  - 401·403(키 거부, 제품 사용 설정 꺼짐)이면 10분 동안 부르지 않는다.
  - 그 밖의 실패(시간 초과·5xx)가 3번 이어지면 1분 동안 부르지 않는다. 성공하면 실패 횟수를 0 으로 되돌린다.
  - 쉬는 동안의 구간은 이동 시간 `null`, 사유 `KAKAO_SUSPENDED` 다.
  - 캐시 시간·쉬는 시간·횟수는 제안값이다.
