# WORKLOG 작성 절차

Claude Code와 함께 한 작업을 기록하는 절차다. 목적은 두 가지다. 이력서·포트폴리오를 STAR(상황·과제·행동·결과)로 정리하고, AI를 어떻게 활용했는지 남기는 것이다.

이 파일(절차)은 git으로 추적한다. 기록 본문은 저장소에 커밋하지 않는다. 2026-10-27 이전에는 절차가 로컬 `docs/WORKLOG.md` 안에만 있어서, 새로 클론하면 절차를 알 수 없었다. 그래서 절차만 이 파일로 분리했다.

## 1. 보관 구조

| 위치 | 내용 | git |
| --- | --- | --- |
| `docs/worklog-guide.md` (이 파일) | 작성 규칙과 절차 | 추적 |
| `docs/WORKLOG.md` | 진행 중 버퍼(아직 아카이브로 옮기지 않은 엔트리), 미해결 `[확인]` 목록, `archived_through` 날짜 | `.gitignore` — 커밋 금지 |
| Notion 아카이브 | 완결된 엔트리 전체(append-only) | — |

- Notion 아카이브 위치는 프로젝트 Notion 아카이브(SSAFY PJT) 아래의 WORKLOG 페이지다. 페이지가 없으면 처음 갱신할 때 사용자에게 위치를 확인한 뒤 만든다 `[확인]`.
- KeyFin(이전 프로젝트)의 기록은 Notion "WORKLOG — reactNativeHaness 작업 기록 (핀테크 RN 하네스)"에 따로 있다. 여기록 기록을 그 페이지에 섞지 않는다.

## 2. 갱신 절차 (트리거: "WORKLOG 갱신해줘")

1. `docs/WORKLOG.md`가 없으면 아래 §3 형식으로 새로 만든다. 맨 위에 `archived_through: 없음`을 둔다.
2. 마지막 갱신 이후의 커밋(`git log`)과 이번 세션의 대화에서 엔트리를 만든다. 엔트리 하나는 의미 있는 작업 하나다.
3. 해석은 사용자가 말한 것만 적는다. 추정에는 `[확인]`을 붙이고, 미해결 `[확인]` 목록에도 올린다.
4. 완결된 엔트리를 Notion 아카이브의 "엔트리" 섹션 맨 끝에 **append**한다.
   - 이미 보관된 엔트리는 고치지 않는다. 정정·보강·`[확인]` 답변은 새 블록으로 append한다.
   - Notion은 저장할 때 파일명·URL을 자동 링크로 바꾼다(`AGENTS.md` → `[AGENTS.md](http://AGENTS.md)`). 그래서 부분 치환은 매칭이 깨진다. 수정하지 말고 append만 쓴다.
5. 보관한 엔트리는 로컬 버퍼에서 지우고, `archived_through`를 마지막으로 보관한 엔트리의 날짜로 바꾼다.

## 3. 엔트리 형식

```markdown
### YYYY-MM-DD · <한 줄 요약>

- 커밋: <해시 또는 "없음 (분석만)"> · 기간: <날짜>
- 작업 방식: <Claude Code 주도 / 보조> (<사용자가 한 것>, <Claude가 한 것>)
- 무엇을 (사실):
  - <코드·실행 결과로 확인한 사실만>
- 왜 / 결정:
  - 사용자: "<사용자 발언 그대로>" → <결정> (대화 YYYY-MM-DD)
- 버린 대안 · 막힌 곳:
  - <시도했지만 버린 것, 막힌 원인과 해결>
- 숫자: <파일 수·줄 수·건수 등 확인한 수치>
- 파생 문장: <이력서·포트폴리오에 쓸 한 문장 — 커밋 해시 포함>
- 태그: <기술·도구>
```

- "무엇을"과 "숫자"에는 확인한 사실만 쓴다. 확인하지 못한 수치는 `TBD`로 적는다.
- "파생 문장"은 STAR의 결과(R)가 드러나게 한 문장으로 쓰고, 근거 커밋을 붙인다.
